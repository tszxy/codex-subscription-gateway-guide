# 06 · 用量透明、账号维护、备份与回滚

[返回首页](../README.md) · 上一章：[错误排障](05-errors-and-troubleshooting.md) · 下一章：[验收测试](07-validation.md)

## 1. 四种“额度/费用”不能混算

| 数据 | 含义 | 应在哪里核对 |
| --- | --- | --- |
| Codex 订阅额度 | 账号计划允许的使用范围、窗口和限制 | 账号官方用量界面/受支持的配额接口 |
| API token 数 | 模型请求输入、缓存与输出规模 | 可信响应 usage、网关统计 |
| CC Switch 估算美元成本 | 用 token 数乘软件配置的模型单价 | CC Switch 的价格设置 |
| 第三方中转账单 | 第三方网站自己实际扣费 | 该网站计费明细和余额变动 |

使用订阅 OAuth 时，CC Switch 出现 `$0.08` 不表示 CPA 已从你某个美元余额扣款。要判断额外收费，必须确认上游认证/计费方式和实际账单，不仅看客户端估算。

本文不把任何第三方站点的“60/60 tokens/3 Hours”解释成 OpenAI 固定计费标准；它可能是站点自己的次数单位。也不承诺订阅按固定“每次请求”扣减，复杂任务、多轮工具调用与长上下文都可能消耗更多。

## 2. 为什么输出很少但输入接近十万 token

Code 模式常在每一轮发送系统提示、工具定义、文件内容、历史消息和工具结果。一次“修复项目”可能产生多条 API 请求；每条继续携带大量上下文。所以短输出并不等于整条请求用量小。

示例：输入 100,000 token、输出 300 token。如果其中 98,000 token 可命中上游缓存，和全部重新处理的用量/费用结构可能差很多。实际计算方式取决于服务的 usage 定义和计费规则，不能只用列表页的 Input/Output 两列推算。

不要把缓存读取与普通输入双重计入；有的 API 将缓存包含在输入总数，有的将其独立展示。记录统计前先确定字段语义。

## 3. 为什么频繁轮换可能消耗更快

缓存是否可复用与账号、上游、模型、请求前缀和缓存 key 等有关。从 A 切到 B 可能需要重建很长上下文；不能假定 A 的缓存自动属于 B。

这也是建议 `fill-first + session-affinity` 的原因：在账号可用时保持连续性，失效后才切换。它只是减少不必要的轮换，不保证缓存始终命中，也不提供固定节省比例。

其他减少浪费的做法：

- 不在同一长会话中反复修改主模型或供应商。
- 小任务使用合适的轻量模型，先确认辅助映射不会影响主任务。
- 长会话必要时压缩上下文/新建清晰任务，但避免无意义地重新注入整个项目。
- 先用低消耗短请求排查连通性，再跑完整 Coding 任务。
- 让客户端、网关和 SDK 的失败重试都保持可控。
- 比较不同服务时使用同样任务、上下文、强度和冷/热缓存条件。

## 4. 怎样记录可对账数据

建议在私有环境维护一张实验表：

| 字段 | 说明 |
| --- | --- |
| 任务编号 | 同一任务相同输入 |
| 请求 ID | 准确关联一条请求，秒级时间不够 |
| 客户端/供应商 | Claude Desktop / CLI，实际网关 |
| 实际模型 | 出站 model 或可信执行日志 |
| 推理强度 | 最终 reasoning 配置 |
| 账号代号 | A/B/C，公开版本不含邮箱 |
| 普通/缓存/输出 token | 按服务字段语义记录 |
| 最终状态与次数 | 区分初始请求、失败重试、辅助请求 |
| 用量/余额前后 | 官方配额或第三方实际账单 |

不应从速度、自述或单条极低价格断言服务一定使用了假模型。同样，不应仅凭菜单叫 Opus 就认定确为 Opus。先对齐计费字段、缓存与路由证据。

## 5. 日常运行检查

每次修改后只做与修改相关的检查：服务运行、真实短请求、模型路由和错误呈现。稳定后不需要持续发推理请求做“心跳”，否则监控自身也消耗用量。

`/healthz` 可做 Caddy 存活监控，但它不检查上游。更深入的健康检查要明确频率、是否消耗配额、是否触发账号切换。本仓库没有默认后台配额轮询或定时推理任务。

日志方面，模板用 journald，保留多久由系统日志配置决定。debug 有利于查询，但仍可能含敏感元数据；保留时间、磁盘上限和访问权限应与你的需求相符。

## 6. 应该备份什么

- CPA 二进制版本号/校验记录，以及私有 `/opt/cpa/config.yaml`。
- `/var/lib/cpa/auths` 的 auth 文件和 `.cds` 状态。
- `/etc/systemd/system/cpa.service` 与错误代理 service。
- `/etc/caddy/Caddyfile`。
- 当前手册/代码 commit，以及部署后冻结的 Python 依赖版本。
- CC Switch 的私有配置备份、本机 query-settings 和只读查询 key。

OAuth 备份具有账号访问能力，需要加密并限制访问。不要把这些内容当作普通配置备份上传公开 GitHub。Caddy 证书数据由其安装方式管理，恢复策略按自己的 Caddy 环境制定。

如果要做一致性备份，先安排短维护窗口停止 CPA，让 auth 刷新和 `.cds` 写入完成，再备份。运行中直接复制可能得到某个时间点不一致的凭证/状态组合。

## 7. 记录 Python 实际版本

requirements 是兼容范围示例，不是所有组合均已测试的锁文件。部署成功后在私有运维记录中保存：

```bash
/opt/codex-gateway/.venv/bin/python --version
/opt/codex-gateway/.venv/bin/python -m pip freeze
/opt/cpa/cli-proxy-api --help
caddy version
git -C /opt/codex-gateway rev-parse HEAD
```

不要把包含真实私有配置的运维目录放进仓库。依赖升级先在测试环境跑离线测试，再做一次实际短请求。

## 8. CPA 升级步骤

1. 阅读新版本 Release 和 config.example，确认 retry、cooldown、OAuth 和转换变化。
2. 备份旧二进制、私有配置、凭证和状态。
3. 下载新版本到独立目录，校验、确认架构，先测试配置。
4. 短维护窗口停止 CPA，替换程序，按需要迁移配置。
5. 启动服务，检查日志、模型列表与一次真实请求。
6. 验证客户端工具调用、推理强度和错误格式没有变化。
7. 失败则停止服务、恢复旧程序和对应配置，重新验证。

不要在没有备份时自动将 latest 覆盖到运行目录。旧程序未必能读取新程序写出的所有状态；回滚应考虑配置/状态兼容性，不能简单宣称换回二进制就一定恢复。

## 9. 错误代理或 Caddy 回滚

错误代理的工作目录已与 CPA 分开。回滚可恢复上一份代码 commit 与依赖，再重启代理；账号凭证目录不受代码 checkout 影响。

若临时绕过错误代理，Caddy 可将 `/v1/*` 直接反代到 8317。先备份、validate，再 reload；这会恢复 CPA 原始错误状态并失去中文终止适配，客户端重试行为可能不同。

不要让公网直接监听 8317/8318 来绕过排障；保持 HTTPS、路径限制和客户端认证。

## 10. 发布仓库时删除了什么

这个公开版本没有真实 VPS IP、账号邮箱、密码、客户端 key、auth JSON、SSH 私钥、数据库、个人请求正文或原始日志。模板域名是 `gateway.example.com`，文档 IP 是 `203.0.113.10`；它们不是可用的公共服务。

仓库只包含原创手册与辅助代码。原来使用的第三方 Claude 网页服务、账号登录信息和客户端内部资源未发布。不要将本仓库描述成可直接复制任何账号或保证长期可用的服务。
